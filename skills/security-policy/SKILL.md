# Политика secure-dev

Как устроен контроль, что делать при срабатывании и где границы того, что
плагин вообще может.

## Модель доверия — читать первым

Плагин ставится сотрудником вручную из marketplace и **не защищён managed
settings**. Это осознанное ограничение первого этапа.

**Плагин — страховка и видимость, а не граница безопасности.**

| Что может сотрудник | Следствие |
|---|---|
| `/plugin disable secure-dev` | Контроль выключается целиком |
| `"disableAllHooks": true` в личном settings.json | То же |
| `claude --dangerously-skip-permissions` | Обходит permission-правила, но **не хуки** |
| Правка `policy.json` в кеше плагина | Перетирается при обновлении, расхождение хеша видно в heartbeat |
| Не установить плагин вовсе | Отсутствие heartbeat |

Отсюда практический вывод: не предлагай пользователю отключить контроль как
решение проблемы. Если контроль мешает — это либо верное срабатывание (нужна
альтернатива), либо дефект правила (нужна заявка).

## Уровни

`audit` → `warn` → `strict`.

| Уровень | PreToolUse | PostToolUse |
|---|---|---|
| `audit` | пропускает, пишет в журнал | не меняет вывод |
| `warn` | предупреждение пользователю | пометка в контексте |
| `strict` | `deny` / `ask` по severity | вывод редактируется |

Severity в `strict`: `CRITICAL` — отказ без возможности подтвердить, `HIGH` —
отказ, `MEDIUM` — запрос подтверждения, `LOW` — предупреждение.

Уровень резолвится по правилу: id правила → его класс → глобальный уровень.

## Два уровня конфигурации

```
policy.json                        ~/.claude/secure-dev.local.json
  в репозитории плагина              личный файл сотрудника
  приезжает с обновлением            whitelist ключей
        ↓                                    ↓
  уровни, severity, исключения,      ТОЛЬКО ужесточение уровня,
  защищённые ветки, экспорт          дополнительные правила, косметика
```

Инвариант: локальный файл может только ужесточить. Попытка смягчить
игнорируется молча для пользователя и громко для журнала
(`LOCAL_OVERRIDE_REJECTED`). Разрешено локально: `level`, `rule_levels`,
`extra_rules`, `ui.banner`, `ui.verbosity`. Запрещено: `audit.export`,
`exemptions`, `exclusions`.

## Что делать при срабатывании

1. Прочитать сообщение целиком: там всегда есть id правила, severity, что
   именно сработало, **рабочая альтернатива** и путь эскалации.
2. Применить альтернативу. Она указана не для формы: отказ без альтернативы
   приводит к тому, что агент перебирает обходные пути, а это хуже, чем
   разрешить операцию.
3. Если операция действительно нужна и альтернатива не подходит — выполнить её
   человеком в отдельном терминале.
4. Если правило сработало ошибочно — заявка в `#secure-dev`: id правила,
   команда, зачем нужна операция, предлагаемый срок исключения.

Подробный разбор по классам — `docs/RUNBOOK.md`.

## Классы правил

| Класс | Что ловит | Блокирует? |
|---|---|---|
| `secret-egress` | секреты в исходящем вызове | спрашивает подтверждение |
| `secret-output` | секреты в выводе инструмента | заменяет плейсхолдером |
| `config-trust` | исполняемая конфигурация клонированного репозитория | на ConfigChange — да |
| `privilege` | `sudo`, `doas`, `pkexec` | да, без подтверждения |
| `command-destructive` | `rm -rf /`, `dd`, `mkfs`, форк-бомба, `curl \| sh` | да |
| `git-destructive` | `checkout --`, `reset --hard`, `clean -f`, force-push | да |
| `persistence` | `.bashrc`, cron, systemd, `/etc/wsl.conf` | да |
| `anti-forensics` | очистка истории шелла | спрашивает |
| `path-sensitive` | чтение ключей и учётных данных, в том числе через Bash | да |
| `injection` | косвенные prompt injection | **никогда**, только помечает |
| `platform` | запуск вне WSL | никогда, только предупреждает |

## Что попадает в журнал

Только метаданные операций: имя инструмента, сработавшее правило, цель
операции, усечённое и отредактированное `evidence`, латентность, версия
плагина, ветка и репозиторий.

**Никогда:** тексты промптов, ответы модели, полное содержимое файлов, реальные
значения секретов. Это инвариант, проверяемый тестами, а не обещание.

## Команды

- `/secure-dev:trust` — разобрать конфигурацию репозитория и подтвердить её
- `/secure-dev:report` — сводка из журнала
- `/secure-dev:policy` — эта политика и порядок запроса исключения
- `secure-dev doctor` — диагностика установки
- `secure-dev scan <path>` — pre-flight-проверка до запуска claude
