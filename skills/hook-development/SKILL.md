# Разработка хуков Claude Code

Хук — это внешняя программа, которую Claude Code вызывает на событиях жизненного
цикла (перед/после инструмента, при отправке промпта, при остановке и т.д.). Хук
получает JSON на **stdin** и влияет на поведение через **код выхода** и/или JSON
на **stdout**. Хуки — часть доверенной периферии: ошибка в хуке ломает или
искажает работу во всех сессиях. Поэтому каждое изменение обязано проверяться
тестами.

## 📍 Сначала область действия: проект или глобально?

Хуки живут в двух местах с разным радиусом действия:

- **Глобально** — `~/.claude/hooks/` + `~/.claude/settings.json`. Действует во
  всех проектах пользователя на этой машине.
- **Локально в проекте** — `<project>/.claude/hooks/` + `<project>/.claude/settings.json`
  (или `settings.local.json`). Действует только в этом репозитории.

Это решение с реальными последствиями (глобальный хук может неожиданно
сработать в чужом, не относящемся к делу проекте), поэтому **если пользователь
явно не указал область действия — спроси, прежде чем создавать файлы или
писать в settings.json.** Не угадывай и не выбирай область по умолчанию молча.
Ориентиры для вопроса:

- Хук про конкретный проект (специфичные для него секреты, стек, workflow) →
  скорее всего локально.
- Хук общего назначения (маскировка секретов, стиль коммитов, общие политики
  безопасности) → скорее всего глобально.
- Если в разговоре уже явно фигурирует путь (`~/.claude/...` или
  `./.claude/...`, «глобально», «только в этом проекте») — область указана,
  вопрос не нужен.

## ⛓️ Железное правило: изменил хук → прогони его батарею

В этом окружении установлен мета-хук `hook_test_runner.py` (PostToolUse на
`Write|Edit|MultiEdit`). После **каждого** изменения файла под `.claude/hooks/`
он автоматически запускает соответствующую **батарею тестов** и **блокирует**
(exit 2, фидбэк модели) при провале. Соглашение:

```
.claude/hooks/<name>.py          ← хук
.claude/hooks/<name>.tests.py    ← его батарея (exit 0 = всё прошло, ≠0 = провал)
```

Также ищется `.claude/hooks/tests/<name>.tests.py`. Поддерживаются `.py .sh .js .mjs`.

Из этого следует рабочий цикл (**сначала тесты**):

1. Создавая новый хук `foo.py`, сразу создай `foo.tests.py` — иначе раннер выдаст
   напоминание об отсутствии батареи.
2. Меняя хук, дай авто-раннеру прогнать батарею; если он вернул провал —
   исправляй, пока не станет зелёным. Не обходи проверку.
3. Батарею можно прогнать и вручную: `python3 .claude/hooks/foo.tests.py`.

Если добавляешь новый хук — **расширь его батарею новыми кейсами до/вместе с
правкой логики**, а не после.

## Анатомия хука (кратко)

- **stdin**: JSON с `hook_event_name`, `tool_name`, `tool_input`, `tool_response`
  (для Post*), `session_id`, `cwd`, `transcript_path`, `permission_mode` и
  событийными полями.
- **Код выхода**: `0` — успех (stdout-JSON применяется); `2` — блокирующая ошибка
  (stderr → модели как фидбэк, для Pre/PostToolUse, UserPromptSubmit, Stop и др.);
  прочее — неблокирующая ошибка (первая строка stderr показывается пользователю).
- **stdout-JSON**: `hookSpecificOutput` (событийные поля), `systemMessage`,
  `suppressOutput`, `continue`. Для `PreToolUse` — `permissionDecision`
  (`allow`/`deny`/`ask`; `defer` — только неинтерактивный режим) и
  `permissionDecisionReason`. Для `PostToolUse` — `updatedToolOutput`
  (принимает и объект, и строку — отдавай ТЕМ ЖЕ типом, что пришёл в
  `tool_response`), `additionalContext`, `decision`/`reason`.

Полный справочник со всеми событиями, полями и матчерами — в
[reference.md](reference.md). Читай его, когда нужен точный контракт события.

## Чек-лист создания хука

0. **Область действия.** Если не указана явно — спроси (см. раздел выше), не
   выбирай молча.
1. **Событие и матчер.** Выбери минимально достаточное событие. Матчер в
   settings.json: точные имена и `A|B` — по буквам; спецсимволы → JS-regex
   (`mcp__.*`, `^Notebook`). Для не-tool событий матчер фильтрует другое поле
   (источник сессии, имя файла и т.п. — см. reference.md).
2. **Fail-open.** Оберни всё в try/except → `exit 0` при внутренней ошибке. Хук
   НИКОГДА не должен ломать сессию из-за своего бага. (Осознанная блокировка —
   `exit 2` — это не то же самое, что баг.)
3. **Не доверяй форме входа.** Поля могут отсутствовать или быть другого типа.
   Проверяй `isinstance`, используй `.get(...)`.
4. **Тип вывода.** Для `updatedToolOutput` сохраняй тип (`dict`↔`dict`,
   `str`↔`str`). Не сериализуй объект в строку без нужды.
5. **Идемпотентность.** Повторный прогон на уже обработанном входе не должен
   ломать результат (напр. не переобрабатывай уже вычищенное).
6. **Побочные эффекты минимальны и безопасны.** Логи — с ограниченными правами,
   без утечки чувствительных данных.
7. **Батарея тестов** рядом с хуком (см. ниже).

## Методология тестирования (что покрывать)

Батарея — обычный скрипт: печатает PASS/FAIL, копит провалы, `sys.exit(1)` если
есть хоть один провал, иначе `0`. Проверяй хук ДВУМЯ способами: (а) импортом
чистых функций напрямую, (б) полным событием через `subprocess` со stdin-JSON.

Обязательные разделы для типового хука:

- **Позитивы** — каждое, что хук ДОЛЖЕН поймать/изменить, срабатывает.
- **Истинные негативы** — валидный безобидный вход не трогается.
- **Ложные срабатывания на реальных данных** — самый важный раздел. Прогони хук
  на образцах того, что он будет видеть в бою (для контент-хуков — куски
  настоящего кода, конфигов, `.env`), и убедись, что он их НЕ портит.
- **Форма вывода** — структурный (`{stdout,stderr}`) и строковый вход
  обрабатываются и сохраняют тип.
- **Решения** — правильные `permissionDecision`/`decision`/коды выхода на
  граничных случаях; отсутствие ложной блокировки.
- **Отказоустойчивость** — пустой stdin, битый JSON, неизвестное событие →
  `exit 0`.
- **Идемпотентность/регрессии** — фиксируй каждый пойманный баг отдельным кейсом.

Шаблоны для старта:
[templates/hook_template.py](templates/hook_template.py) и
[templates/hook_tests_template.py](templates/hook_tests_template.py).

## Валидация перед подключением

1. `python3 -c "import json,ast; ast.parse(open('foo.py').read())"` — синтаксис.
2. Прогнать батарею вручную — зелёно.
3. `python3 -c "import json;json.load(open('settings.json'))"` — settings.json
   остаётся валидным JSON после регистрации.
4. Проверить хук на «сухом» событии: скормить ему пример JSON на stdin и глазами
   оценить stdout/код выхода. Для трассировки — `claude --debug`.
5. Помни: хуки грузятся при старте сессии (изменения settings.json могут
   подхватываться живьём, но код хука перезапускается на каждый вызов —
   правки логики активны сразу).

## Как работает авто-раннер и как подключить новый хук

`hook_test_runner.py` на `PostToolUse(Write|Edit|MultiEdit)`:
не-хук файл → тихий no-op; хук без батареи → напоминание; батарея есть и зелёная
→ тихий `✅`; батарея красная → `exit 2` с отчётом в stderr (модель обязана
починить).

Чтобы новый хук попал под авто-проверку — достаточно назвать батарею по
соглашению (`<name>.tests.py` рядом). Ничего регистрировать не нужно.

## Типичные ошибки

- Хук падает и роняет сессию (нет fail-open).
- Слишком широкий матчер/regex → срабатывает не на том.
- `updatedToolOutput` строкой вместо объекта → инструмент получает искажённый тип.
- Регэксп-детекторы, ловящие обычный код (проверяй раздел «ложные срабатывания»!).
- Блокировка (`exit 2`) там, где хватило бы `systemMessage`.
- Недокументированные значения решений (напр. `permissionDecision:"defer"` в
  интерактиве) — используй только задокументированные.
- Батарея не покрывает реальные входные данные, только синтетику.
