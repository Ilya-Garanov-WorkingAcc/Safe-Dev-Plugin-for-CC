# Разработка хуков Claude Code

Хук — внешняя программа на событии жизненного цикла Claude Code: JSON на
stdin → код выхода + JSON на stdout. Хуки — доверенная периферия: баг в одном
хуке ломает или искажает работу во ВСЕХ сессиях. Поэтому каждое изменение
обязано проверяться тестами.

## 0. Область действия — спроси, если не указана

- **Глобально**: `~/.claude/hooks/` + `~/.claude/settings.json` — все проекты.
- **Локально**: `<project>/.claude/hooks/` + `<project>/.claude/settings.json`.

Если пользователь явно не назвал область (нет пути, нет слов
«глобально»/«только в этом проекте») — **спроси, не выбирай молча**:
глобальный хук может неожиданно сработать в чужом проекте. Ориентир: правки
под конкретный проект → локально; секреты/безопасность/стиль коммитов общего
назначения → глобально.

## Железное правило: изменил хук → прогони батарею

Мета-хук `hook_test_runner.py` (PostToolUse на `Write|Edit|MultiEdit`) реагирует
на любую правку под `.claude/hooks/`:

```
.claude/hooks/<name>.py          ← хук
.claude/hooks/<name>.tests.py    ← батарея (exit 0 = ок, ≠0 = блок)
```
(или `.claude/hooks/tests/<name>.tests.py`; поддержаны `.py .sh .js .mjs`)

- Не-хук файл → тихий no-op.
- Хук без батареи → напоминание создать её.
- Батарея зелёная → тихое подтверждение.
- Батарея красная → **блокирует** (`exit 2`, фидбэк модели). Не обходи —
  чини, пока не позеленеет.

Отсюда рабочий цикл: новый хук `foo.py` → сразу `foo.tests.py`; новая логика →
новые кейсы В ТОТ ЖЕ момент, не после. Ручной прогон:
`python3 .claude/hooks/foo.tests.py`. Ничего регистрировать не нужно — авто-раннер
находит батарею по имени.

## Анатомия хука (кратко)

- **stdin**: JSON с `hook_event_name`, `tool_name`, `tool_input`, `tool_response`
  (для Post*), `session_id`, `cwd`, `transcript_path`, `permission_mode` и
  событийными полями.
- **Код выхода**: `0` — успех (stdout-JSON применяется); `2` — блокирующая ошибка
  (stderr → модели как фидбэк, для Pre/PostToolUse, UserPromptSubmit, Stop и др.);
  прочее — неблокирующая ошибка (первая строка stderr показывается пользователю).
- **stdout-JSON**: `hookSpecificOutput` (событийные поля), `systemMessage`,
  `suppressOutput`, `continue`. Для `PreToolUse` — `permissionDecision`
  (`allow`/`deny`/`ask`; `defer` — только неинтерактивный режим) и
  `permissionDecisionReason`. Для `PostToolUse` — `updatedToolOutput`
  (принимает и объект, и строку — отдавай ТЕМ ЖЕ типом, что пришёл в
  `tool_response`), `additionalContext`, `decision`/`reason`.

Полный справочник со всеми событиями, полями и матчерами — в
[reference.md](reference.md). Читай его, когда нужен точный контракт события.

## Чек-лист создания хука

0. **Область действия.** Не указана явно — спроси (см. выше).
1. **Событие и матчер.** Минимально достаточное событие. Матчер: точные имена
   и `A|B` — по буквам; спецсимволы → JS-regex (`mcp__.*`, `^Notebook`).
2. **Fail-open.** Весь код в try/except → `exit 0` при внутренней ошибке.
   Осознанный `exit 2` — не баг.
3. **Защитный парсинг входа.** Поля могут отсутствовать/быть другого типа —
   `isinstance`, `.get(...)`.
4. **Тип вывода.** `updatedToolOutput` сохраняет тип (`dict`↔`dict`, `str`↔`str`).
5. **Идемпотентность.** Повторный прогон на уже обработанном входе не портит результат.
6. **Побочные эффекты минимальны.** Логи — ограниченные права, без утечки данных.
7. **UTF-8 явно, если есть не-ASCII.** В начале файла:
   `for s in (sys.stdin, sys.stdout, sys.stderr): s.reconfigure(encoding="utf-8", errors="replace")`,
   плюс `json.dumps(obj, ensure_ascii=True)` при выдаче stdout-JSON. Без этого
   на Windows-консоли (cp1251/cp1252/cp437) хук молча теряет JSON-решение —
   fail-open (п.2) проглатывает `UnicodeEncodeError`, и, например, секрет
   доходит до модели немаскированным. Детали и как тестировать —
   [reference.md](reference.md#кодировка-консоли-не-utf8-windows).
8. **Батарея тестов** рядом с хуком (см. ниже).

## Методология тестирования (что покрывать)

Батарея — обычный скрипт: печатает PASS/FAIL, копит провалы, `sys.exit(1)` если
есть хоть один провал, иначе `0`. Проверяй хук ДВУМЯ способами: (а) импортом
чистых функций напрямую, (б) полным событием через `subprocess` со stdin-JSON.

- **Позитивы** — каждое, что хук ДОЛЖЕН поймать/изменить, срабатывает.
- **Истинные негативы** — валидный безобидный вход не трогается.
- **Ложные срабатывания на реальных данных** — самый важный раздел. Прогони хук
  на образцах того, что он увидит в бою (для контент-хуков — куски настоящего
  кода, конфигов, `.env`), и убедись, что он их НЕ портит.
- **Форма вывода** — структурный (`{stdout,stderr}`) и строковый вход
  обрабатываются и сохраняют тип.
- **Решения** — правильные `permissionDecision`/`decision`/коды выхода на
  граничных случаях; отсутствие ложной блокировки.
- **Отказоустойчивость** — пустой stdin, битый JSON, неизвестное событие →
  `exit 0`.
- **Кодировка** — если есть не-ASCII, повтори кейсы под
  `env={"PYTHONIOENCODING": "cp1251"}` (и `cp1252`/`cp437`) через
  `subprocess.run(..., env=env)`: код выхода/решение должны совпасть с
  UTF-8-прогоном. Эмулирует Windows-консоль на Linux/macOS.
- **Идемпотентность/регрессии** — фиксируй каждый пойманный баг отдельным кейсом.

Шаблоны для старта:
[templates/hook_template.py](templates/hook_template.py) и
[templates/hook_tests_template.py](templates/hook_tests_template.py).

## Валидация перед подключением

1. `python3 -c "import json,ast; ast.parse(open('foo.py').read())"` — синтаксис.
2. Прогнать батарею вручную — зелёно.
3. `python3 -c "import json;json.load(open('settings.json'))"` — settings.json
   остаётся валидным JSON после регистрации.
4. Проверить хук на «сухом» событии: скормить ему пример JSON на stdin и глазами
   оценить stdout/код выхода. Для трассировки — `claude --debug`.
5. Хуки грузятся при старте сессии — правки логики активны сразу (перезапуск
   процесса на каждый вызов), но для эффекта в ТЕКУЩЕЙ сессии нужен рестарт.

## Типичные ошибки

- Хук падает и роняет сессию (нет fail-open).
- Слишком широкий матчер/regex → срабатывает не на том.
- `updatedToolOutput` строкой вместо объекта → инструмент получает искажённый тип.
- Регэксп-детекторы, ловящие обычный код (проверяй раздел «ложные срабатывания»!).
- Блокировка (`exit 2`) там, где хватило бы `systemMessage`.
- Недокументированные значения решений (напр. `permissionDecision:"defer"` в
  интерактиве) — используй только задокументированные.
- Батарея не покрывает реальные входные данные, только синтетику.
- Не-ASCII в stdout без `reconfigure` — на Windows-консоли хук молча теряет
  решение (см. п.7 чек-листа).
