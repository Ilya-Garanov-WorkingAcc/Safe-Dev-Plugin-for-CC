# ARCHITECTURE.md — secure-dev v2.0 (пилотная конфигурация)

Плагин безопасной разработки для Claude Code. Преемник `safe-development` v1.x.

**Статус:** проект архитектуры, до реализации
**Развёртывание:** ручная установка из приватного marketplace, без managed settings
**Платформа:** WSL2/Ubuntu — жёсткое требование
**Аудитория:** отдел разработки, пилот 3–5 человек с последующим расширением

---

## 1. Контекст

### 1.1 Что меняется относительно v1.x

v1.x — персональный плагин: анонимизация секретов плюс принудительная тест-батарея
для хуков. Одна угроза, решённая хорошо.

v2.0 — отраслевые практики безопасной работы с агентом, собранные в один инструмент.
Плагин синтезирует контроли из шести проанализированных источников (§10) и добавляет
один, отсутствующий во всех: проверку целостности конфигурации репозитория.

### 1.2 Модель доверия пилота — читать первым

Плагин ставится сотрудником вручную из marketplace и **не защищён managed settings**.
Это осознанное ограничение первого этапа, и оно определяет всю архитектуру.

**Плагин — страховка и видимость, а не граница безопасности.**

| Что может сотрудник | Следствие |
|---|---|
| `/plugin disable secure-dev` | Контроль выключается целиком |
| `"disableAllHooks": true` в личном `settings.json` | То же |
| `claude --dangerously-skip-permissions` | Обходятся permission-правила, но **не хуки** — они продолжают работать |
| Отредактировать `policy.json` в кеше плагина | Перетирается при обновлении, расхождение хеша видно в heartbeat |
| Не установить плагин вовсе | Отсутствие heartbeat |

**Что работает в полном объёме:** блокировка на `PreToolUse` (команды, пути, egress
секретов), редактирование вывода на `PostToolUse`, блокировка `ConfigChange` внутри
сессии, аудит и heartbeat.

**Ключевой механизм — не запрет, а видимость.** Плагин пишет heartbeat при каждом
старте сессии. Отключивший его сотрудник перестаёт появляться в сводке. Это переводит
вопрос из технической плоскости, где без managed settings он не решается, в
управленческую, где рычаг есть.

Дорога к жёсткому enforcement — в `ROADMAP.md`, требует MDM/GPO, вне периметра пилота.

### 1.3 Цели

| # | Цель | Проверяемый критерий |
|---|---|---|
| G1 | Секреты не покидают периметр | Ни один секрет не уходит в исходящий вызов и не попадает в контекст без подтверждения |
| G2 | Агент не разрушает рабочую машину | Деструктивные команды блокируются по семантике, а не regex |
| G3 | Клонированный репозиторий виден до запуска | Опасная конфигурация обнаруживается pre-flight-сканом и на `SessionStart` |
| G4 | Косвенные инъекции видимы | Инструкции в README, веб-выводе и ответах MCP помечаются в контексте |
| G5 | События восстановимы | JSONL-аудит, пригодный для разбора и для SIEM в будущем |
| G6 | Факт работы контроля наблюдаем | Heartbeat: версия плагина, хеш политики, счётчики |
| G7 | Контроль не саботируется | Раскатка `audit → warn → strict` по измеренной доле ложных срабатываний |

### 1.4 Не-цели

- **Статический анализ уязвимостей в написанном коде** (SQLi, XSS, RCE) — ADR-004.
- **Контроль дублирования и качества кода** — это `devflow/consistency.py`.
- **Изоляция процесса** — sandbox, сетевой прокси, контейнеры: слой ОС.
- **Замена secret scanning в CI** — gitleaks/trufflehog остаются; плагин закрывает окно
  между генерацией секрета агентом и коммитом.
- **Поддержка нативного Windows и PowerShell** — §1.5.

### 1.5 Платформа: только WSL

Работа Claude Code вне WSL на рабочих машинах отдела запрещена политикой.
Плагин детектирует нарушение (`platform_guard`) и предупреждает.

Обоснование:

- **Одна цель для парсера команд.** Разбор `cmd.exe` и PowerShell — второй лексер,
  другая модель кавычек, другие правила экранирования, удвоение корпуса тестов на
  обходы. Около четверти общего объёма разработки при нулевом приросте ценности,
  если WSL доступен всем.
- **Скрытая подмена шелла.** Хуки Claude Code по умолчанию используют bash, но на
  Windows без установленного Git Bash автоматически переключаются на PowerShell.
  Один и тот же хук на разных машинах исполнялся бы разным интерпретатором —
  неприемлемо для контроля безопасности.
- **Семантика путей.** Регистронезависимость, `\` и `/`, буквы дисков, UNC,
  различие `~` — удваивают поверхность `path_guard` и `config_trust`.
- **Единая точка аудита.** Одно расположение `~/.claude`, один формат путей.

## 2. Модель угроз

| ID | Угроза | Вектор | Контроль | Покрытие |
|---|---|---|---|---|
| T1 | Кража учётных данных через контекст | Чтение `.env`, вывод `printenv`, ответ API с токеном | `secret_redactor` (PostToolUse) | полное |
| T2 | Эксфильтрация секрета наружу | `curl -H "Authorization: …"`, WebFetch с токеном в URL, MCP-вызов | `secret_redactor` (PreToolUse, `ask`) | полное |
| T3 | **RCE из клонированного репозитория** | Вредоносный `.claude/settings.json` с хуком, `.mcp.json` с командой запуска, `.claude/hooks/*`. CVE-2025-59536, CVE-2025-59356, CVE-2026-21852 | `secure-dev scan` (pre-flight) + `config_trust` | **частичное**, §4.3 |
| T4 | Разрушение рабочей машины | `rm -rf ~`, `dd of=/dev/sda`, форк-бомба, `chmod -R 777 /` | `command_guard` | полное |
| T5 | Потеря работы в git | `git checkout --`, `reset --hard`, `clean -fdx`, force-push в main | `command_guard`, класс `git-destructive` | полное |
| T6 | Косвенная prompt injection | Инструкции в README, HTML-комментариях, выводе команды, ответе MCP; base64, гомоглифы, zero-width | `injection_scanner` | полное (детект, не блок) |
| T7 | Отравленный MCP-сервер | Tool poisoning, rug pull, вредоносное описание инструмента | `config_trust` (детект в `.mcp.json`) + `enableAllProjectMcpServers: false` в шаблоне | частичное |
| T8 | Эскалация до root | `sudo` из агента; в WSL обычно **без пароля** | `command_guard`, правило `command-sudo`, `CRITICAL` | полное |
| T9 | Персистентность через shell-конфиг | Дозапись в `~/.bashrc`, `.zshrc`, `.profile`, `.envrc` | `command_guard` + `path_guard` + шаблон настроек | полное |
| T10 | Обход через субагента | Субагент делает то, что заблокировано в main-thread | Все хуки читают `agent_id`/`agent_type`, политика **идентична** | полное |
| T11 | Отключение контроля сотрудником | `/plugin disable`, `disableAllHooks` | Heartbeat → видимость, не запрет | **технически не закрывается** |

### 2.1 Про T8 и WSL отдельно

На обычной Linux-станции `sudo` из агента упёрся бы в запрос пароля, а неинтерактивный
шелл хука его не пройдёт. **В типовой WSL-Ubuntu пользователь по умолчанию имеет
passwordless sudo** через `/etc/sudoers.d/`. То есть в целевой среде `sudo` из агента
отрабатывает молча и сразу даёт root.

Последствия: необратимое разрушение за пределами `$HOME`; персистентность через cron,
systemd, `/etc/profile.d`; отключение самих контролей; правка `/etc/wsl.conf` и
перемонтирование дисков Windows — то есть выход в файловую систему хоста.

**Решение: полный запрет `sudo` для агента, severity `CRITICAL`, без возможности
подтвердить.** Эскалация — человеком в отдельном терминале. Реальная потребность
(`apt install`, `systemctl` для локальных сервисов) эпизодическая, стоимость ручного
выполнения — секунды.

Рекомендация в `ROLLOUT.md`, но не техническое требование: убрать `NOPASSWD` из
sudoers WSL. Это делает запрет двухслойным.

## 4. Карта хуков

Один Python-файл на модуль; ветвление по `hook_event_name`, как в `secret_redactor.py` v1.x.

| Событие | Матчер | Модуль | Решение | Fail-mode |
|---|---|---|---|---|
| `SessionStart` | `startup\|resume\|clear\|fork` | `session_guard.py` | баннер, `additionalContext`, **heartbeat** | open |
| `SessionStart` | `startup\|resume\|fork` | `config_trust.py` | `additionalContext` (отчёт о доверии) | closed |
| `SessionStart` | `startup` | `platform_guard.py` | `additionalContext` при не-WSL | open |
| `ConfigChange` | `project_settings\|local_settings\|user_settings\|skills` | `config_trust.py` | `decision: "block"` | closed |
| `PreToolUse` | `Bash` | `command_guard.py` | `deny` / `ask` | **closed** |
| `PreToolUse` | `Read\|Glob\|Grep\|Bash` | `path_guard.py` | `deny` | **closed** |
| `PreToolUse` | `Bash\|WebFetch\|WebSearch\|Write\|Edit\|MultiEdit\|mcp__.*` | `secret_redactor.py` | `ask` / `systemMessage` | open |
| `PostToolUse` | `*` | `secret_redactor.py` | `updatedToolOutput` | open |
| `PostToolUse` | `Read\|WebFetch\|Bash\|mcp__.*` | `injection_scanner.py` | `additionalContext` | open |
| `PostToolUse` | `Write\|Edit\|MultiEdit` | `hook_test_runner.py` | `exit 2` | open |
| `SubagentStart` | `*` | `session_guard.py` | `additionalContext` | open |
| `SessionEnd` | `*` | `audit_flush.py` | — (async) | open |

### 4.1 Fail-open против fail-closed

Инвариант:

- **Модули, которые редактируют или предупреждают → fail-open.** Сбой хука не должен
  ломать работу Claude Code. Реализовано в v1.x, сохраняется.
- **Модули, которые блокируют → fail-closed.** Если `command_guard` упал на разборе
  команды, он обязан вернуть `ask`, а не пропустить. Иначе атакующий подбирает вход,
  роняющий парсер, и получает обход.

Промежуточный режим для fail-closed — `ask`, а не `deny`: баг плагина не должен
останавливать работу команды. `ask` перекладывает решение на человека и пишет
`PARSER_ERROR` в аудит. Причина ошибки идёт в лог, не в сообщение пользователю —
текст ошибки парсера служит подсказкой атакующему.

### 4.2 Параллелизм

Claude Code запускает совпавшие хуки параллельно, порядок не гарантирован. Следствия:

- Модули не полагаются на порядок друг относительно друга.
- Конфликт решений разрешается в сторону наиболее ограничительного
  (`deny` > `ask` > `allow`), но два `updatedToolOutput` на одном событии —
  неопределённое поведение.
- **Поэтому `secret_redactor` — единственный модуль, возвращающий `updatedToolOutput`.**
  `injection_scanner` на том же событии возвращает `additionalContext`, который
  аккумулируется без конфликта. Нормализация обфускации (TS.md §9.2) выполняется
  только при отсутствии конфликта; координация — через session-state по `tool_use_id`.

### 4.3 Гонка `SessionStart` — известное ограничение T3

`config_trust` на `SessionStart` запускается **параллельно** с вредоносным хуком того
же события из `.claude/settings.json` клонированного репозитория, а не до него.
В первой сессии в незнакомом репозитории детект происходит пост-фактум.

Компенсации, в порядке эффективности:

1. **Pre-flight `secure-dev scan`** — единственный контроль до запуска. Раздаётся
   shell-функцией, оборачивающей `claude`: при входе в каталог без записи в реестре
   доверия сначала выполняется скан. Обходится тривиально (вызов бинарника напрямую),
   но закрывает основной сценарий — неумышленный.
2. **Встроенный workspace trust dialog Claude Code** — гейтит project allow-правила и
   хуки из frontmatter субагентов. Частичная нативная защита; на `hooks` в
   `.claude/settings.json` распространяется не полностью.
3. **`config_trust` на `ConfigChange`** — блокирует изменения **внутри** сессии,
   здесь гонки нет.

Полное закрытие T3 требует managed `allowManagedHooksOnly` — первый пункт `ROADMAP.md`.

### 5.1 Ответственности ядра

| Модуль | Делает | Явно НЕ делает |
|---|---|---|
| `hookio.py` | Читает и валидирует stdin, форсит UTF-8, `emit()`, fail-mode-обёртка | Не знает про правила |
| `config.py` | Сливает `policy.json` с личными оверрайдами, считает хеш политики | Не принимает решений |
| `policy.py` | Резолвит уровень для пары (правило, контекст), исключения, session-memory | Не детектирует |
| `audit.py` | JSONL, маскирование, ротация, heartbeat | Не отправляет наружу |
| `export.py` | `none` / `file` / `http` | Не формирует записи |
| `cmdparse.py` | Разбирает команду в дерево вызовов, нормализует флаги | Не решает, опасна ли |
| `ruleset.py` | Загружает и валидирует `rules/*.json` | Не применяет |

Разделение `cmdparse` (что за команда) и `commands.json` (какие опасны) намеренное:
правила обновляются без изменения Python-кода, а значит без полного цикла ревью
security-критичной логики.

## 6. Двухуровневая конфигурация

Одного редактируемого файла недостаточно: конфиг, который правит сотрудник, —
это политика, которую правит сотрудник.

```
policy.json                            ~/.claude/secure-dev.local.json
  внутри репозитория плагина             личный файл сотрудника
  приезжает с обновлением                schema: whitelist ключей
        ↓                                        ↓
  уровни, severity, исключения,          ужесточение уровня,
  защищённые ветки, exclusions,          дополнительные правила,
  export-настройки, llm.enabled          косметика (баннер, verbosity)
        └──────────► config.merge() ◄───────────┘
                          │
          эффективная политика + sha256(policy.json) → heartbeat
```

Инвариант: локальный файл может только **ужесточить**. Попытка смягчить —
игнорируется и пишет `LOCAL_OVERRIDE_REJECTED` в аудит. Расхождение хеша
`policy.json` с эталоном для версии плагина попадает в heartbeat как `policy_tampered`.

## 7. Потоки данных

### 7.1 Блокировка деструктивной команды

```
Claude → Bash("git checkout -- src/")
   ▼ PreToolUse, matcher "Bash"
command_guard.py
   ├─ cmdparse.parse()   → [Cmd(git, ["checkout","--","src/"])]
   │      раскрыты $(), |, &&, bash -c; нормализованы флаги
   ├─ ruleset.match()    → git-checkout-discard, HIGH
   ├─ policy.resolve()   → strict
   ├─ policy.seen()      → показывали ли это правило+цель в сессии
   ├─ audit.write()      → action="denied"
   └─ deny + причина + рабочая альтернатива + путь эскалации
```

### 7.2 Проверка доверия к репозиторию

```
secure-dev scan <path>              SessionStart              ConfigChange
   (до запуска claude)                  ▼                          ▼
        └────────────────────► config_trust.py ◄───────────────────┘
                                     │
    repo_id = sha256(нормализованный git remote) либо sha256(realpath)
                                     │
    baseline: ${CLAUDE_PLUGIN_DATA}/trust/<repo_id>.json
                                     │
    ├─ нет baseline, горячих ключей нет  → trusted, тихо
    ├─ нет baseline, горячие ключи есть  → pending + отчёт с перечнем
    │                                       конкретных команд и URL
    ├─ есть, совпадает                   → тихо
    └─ есть, разошлось                   → quarantined
                                           SessionStart: отчёт
                                           ConfigChange: decision="block"
```

Хранилище — `${CLAUDE_PLUGIN_DATA}`, а не каталог плагина: каталог плагина
перезаписывается при каждом обновлении, `CLAUDE_PLUGIN_DATA` обновления переживает.
Это же штатно решает проблему v1.x, где путь аудит-лога был захардкожен в `~/.claude/`
именно по этой причине.

### 7.3 Аудит и heartbeat

```
хуки ──► audit.write() ──► ${CLAUDE_PLUGIN_DATA}/audit/YYYY-MM-DD.jsonl  (0600)
                                        │
session_guard ──► heartbeat ────────────┤
   {plugin_version, policy_sha256, policy_tampered, level, rules_count,
    settings_template_applied, wsl, user, host, ts}
                                        │
                        SessionEnd ──► audit_flush.py (async)
                                        ├─ ротация по retention
                                        └─ export: none | file | http
```

Экспорт вынесен в `SessionEnd` и помечен `async`: сетевой вызов внутри `PreToolUse`
добавил бы недопустимую задержку в цикл агента и создал бы новый канал эксфильтрации.

**Что в аудит не попадает никогда:** содержимое промптов, ответы модели, реальные
значения секретов. Только метаданные операций. Это не смягчающая формулировка,
а инвариант, проверяемый тестами (TS.md §14) — и то, что делает фразу
«мониторим агента, а не разработчика» правдой.

Отдельно: у Claude Code есть нативные `type: "http"` хуки, отправляющие вход хука
на URL. **Для аудита они не используются** — они шлют сырые `tool_input`/`tool_response`,
то есть ровно те секреты, которые плагин обязан вычищать. Экспортируется только
обработанный и замаскированный JSONL через `export.py`.

## 8. Архитектурные решения (ADR)

### ADR-001 — Видимость вместо enforcement на первом этапе

**Контекст.** Managed settings требуют MDM/GPO и участия IT; на пилоте недоступны.
**Решение.** Плагин ставится вручную; контроль над отключением обеспечивается
heartbeat и организационно, а не технически.
**Альтернативы.** (а) Ждать MDM — блокирует пилот на неопределённый срок.
(б) Обёртка над `claude` в `$PATH` — обходится вызовом бинарника, ломается при обновлении.
**Последствия.** T11 не закрывается. Плагин обязан быть достаточно полезным и
ненавязчивым, чтобы его не хотелось отключать — отсюда ADR-003, ADR-004 и
session-memory решений. Путь к enforcement — `ROADMAP.md`.

### ADR-002 — Семантический разбор команд вместо regex

**Контекст.** Regex-блэклист (`rm\s+-rf\s+/`) обходится тривиально: `rm -fr /`,
`rm --recursive --force /`, `RM=rm; $RM -rf /`, `bash -c 'rm -rf /'`,
`python3 -c "import os;os.system('rm -rf /')"`, `echo cm0gLXJmIC8= | base64 -d | sh`.
**Решение.** `cmdparse.py` строит дерево вызовов: разбор списков, пайпов и подстановок,
раскрытие обёрток-интерпретаторов, нормализация флагов до канонического набора.
**Альтернативы.** Regex — отвергнут. Аудит на уровне ОС (auditd) — надёжнее, но вне
периметра плагина и требует прав.
**Последствия.** Парсер — самый сложный и самый атакуемый компонент; требует
property-тестов, корпуса обходов и fail-closed на неразобранном входе.
Динамически собранные команды статически неразрешимы — попадают в `ask`.

### ADR-003 — Три уровня enforcement и постепенная раскатка

**Контекст.** Блокирующий контроль, включённый сразу, генерирует поток ложных
срабатываний; первый результат — поиск способов обойти. При добровольной установке
это буквально `/plugin disable`.
**Решение.** `level ∈ {audit, warn, strict}` с per-rule переопределением. Правила
класса `secret-*` — `strict` с первого дня (поведение обкатано в v1.x), остальные —
по графику на основе измеренной точности.
**Последствия.** Нужна метрика доли ложных срабатываний по каждому правилу.
Переход между фазами — по метрике, а не по календарю.

### ADR-004 — Никакого статического анализа уязвимостей в блокирующем хуке

**Контекст.** Популярные плагины блокируют `Write`/`Edit` по regex-совпадению на
20+ категорий OWASP.
**Решение.** Не реализуем.
**Обоснование.** (а) Точность regex на исходном коде без анализа потока данных
принципиально низкая. (б) Блокировка записи файла ломает основной рабочий процесс,
а не побочный — цена ложного срабатывания на порядок выше. (в) Контроль,
срабатывающий на корректный код, обучает игнорировать все предупреждения плагина,
включая верные. При добровольной установке это фатально.
**Компенсация.** `/security-review` в Claude Code, `anthropics/claude-code-security-review`
как GitHub Action, semgrep/bandit в CI. Указывается явно в `ROLLOUT.md`.

### ADR-005 — Правила в данных, а не в коде

**Контекст.** В v1.x правила детекции секретов — литералы в `secret_redactor.py`.
**Решение.** `rules/*.json`, загрузка через `ruleset.py`, валидация по схеме.
**Альтернативы.** YAML читаемее, но требует PyYAML (внешняя зависимость на всех
машинах) или самописного парсера в security-критичном месте. JSON — stdlib.
**Последствия.** Обновление правил = обновление плагина через marketplace, без правки
Python. Схема правил — публичный контракт, версионируется.

### ADR-006 — LLM-проверка через нативные `type: "prompt"` хуки

**Контекст.** Второй слой детекции полезен для неоднозначных случаев. Аналоги
запускают `claude` CLI из хука.
**Решение.** Нативные prompt-хуки Claude Code, только там, где детерминированный
слой вернул «не уверен».
**Альтернативы.** Шелл-вызов CLI — свой ключ, свой таймаут, свой процесс, риск рекурсии.
**Последствия.** Дефолтный таймаут 30 с и стоимость в токенах. Никогда не единственный
контроль: LLM-решение недетерминировано, а G2/G3 требуют детерминизма.
**На пилоте выключено по умолчанию** (`policy.llm.enabled = false`).

### ADR-007 — Только WSL

См. §1.5. Убирает из объёма разработки разбор `cmd.exe`/PowerShell (~25% фазы 2),
устраняет неопределённость с интерпретатором хуков и удвоение семантики путей.
**Последствие.** Требуется организационное решение и `platform_guard`, предупреждающий
при запуске вне WSL.

### ADR-008 — Двухуровневый конфиг с инвариантом «только ужесточение»

См. §6. Альтернатива — один файл — делает политику редактируемой сотрудником,
что обесценивает разграничение уровней.

## 11. Что пересмотреть при росте

- **Managed settings.** Первый пункт `ROADMAP.md`: при появлении MDM/GPO переход на
  `allowManagedHooksOnly` + `enabledPlugins` закрывает T3 полностью и T11 технически.
- **Парсер команд.** При первом подтверждённом обходе — переход на внешнюю проверенную
  реализацию или на sandbox-исполнение вместо статического анализа.
- **Реестр доверия.** Локальный файл не выдерживает сценарий «доверил на ноутбуке,
  не доверил на десктопе». При росте — централизованный реестр с подписью.
- **Экспорт аудита.** `none` → `file` (сетевой шар) → `http` → OTLP.
- **LLM-слой.** Включать, когда детерминированный слой упрётся в потолок точности на
  `injection_scanner`; следить за долей эскалаций (порог ~2% вызовов).
