# ROLLOUT.md — для сотрудника

Что это за плагин, что он делает с вашей работой и что о ней собирает.
Документ написан для чтения целиком: он занимает пять минут и снимает
большинство вопросов заранее.

---

## 1. Зачем

Claude Code выполняет команды и читает файлы на вашей рабочей машине. Четыре
вещи при этом происходят регулярно и не по злому умыслу:

1. Секрет из `.env` или из вывода команды попадает в контекст модели, а оттуда —
   в исходящий вызов.
2. Агент выполняет разрушительную команду: `git checkout --` по несохранённым
   изменениям, `rm -rf` не по тому пути, `git reset --hard`.
3. Клонированный репозиторий приносит `.claude/settings.json` с хуком или
   `.mcp.json` с командой запуска — и они исполняются при первом же старте
   сессии, до того как вы что-либо увидели.
4. В README, в веб-странице или в ответе MCP-сервера лежит текст, написанный
   для агента, а не для вас.

Плагин закрывает эти четыре сценария. Он не проверяет ваш код на уязвимости и
не оценивает его качество — для этого есть `/security-review` и CI.

---

## 2. Что вы увидите

**При старте сессии** — рамка с состоянием:

```
┌─ secure-dev 2.0.0 ────────────────────────────
│ Режим: AUDIT      Правил: 56
│ Политика: 2026.07-pilot
│ Репозиторий: corp/stocks_agent  [доверенный]
│ Экспорт аудита: локально
└────────────────────────────────────────────
```

Баннер отключается: `~/.claude/secure-dev.local.json` → `{"ui": {"banner": false}}`.

**При срабатывании правила** — сообщение, в котором всегда есть: id правила,
severity, что именно сработало, **рабочая альтернатива** и путь эскалации.
Если альтернативы нет — это дефект правила, сообщите о нём.

**В незнакомом репозитории с исполняемой конфигурацией** — перечень ключей и
конкретных команд и URL, которые будут выполнены, с предложением подтвердить
их через `/secure-dev:trust`.

## 3. Что собирается в журнал

Журнал лежит **локально**: `${CLAUDE_PLUGIN_DATA}/audit/YYYY-MM-DD.jsonl`,
права `0600`. На этапе пилота он никуда не отправляется (`export: none`).

Одна запись — одно срабатывание правила:

```json
{
  "kind": "event",
  "ts": "2026-07-28T14:22:31.482+03:00",
  "user": "i.garanov",
  "host": "DESKTOP-7A2K",
  "cwd": "/home/ilya/projects/stocks_agent",
  "repo": "github.com/corp/stocks_agent",
  "git_branch": "feat/ingest",
  "hook": "command_guard",
  "tool": "Bash",
  "rule": "git-checkout-discard",
  "severity": "HIGH",
  "action": "denied",
  "target": "src/",
  "evidence": "git checkout -- src/",
  "latency_ms": 41
}
```

Плюс одна запись heartbeat на старт сессии: версия плагина, версия и хеш
политики, уровень, число правил, признак WSL, факт применения рекомендуемых
настроек.

### Чего в журнале нет никогда

- Текстов ваших запросов к модели.
- Ответов модели.
- Полного содержимого файлов.
- Реальных значений секретов — только тип и маска вида `AKIA…LE`.

Это не смягчающая формулировка, а инвариант: в тест-батарее каждого модуля
есть негативный кейс на утечку, и релиз с такой утечкой не соберётся.

Проверить самостоятельно можно в любой момент:

```bash
secure-dev report --week
cat ~/.claude/plugins/*/data/audit/*.jsonl | jq -r '.rule' | sort | uniq -c | sort -rn
```

### Зачем heartbeat

Плагин ставится вручную и отключается одной командой. Технически запретить это
на пилоте нельзя. Heartbeat отвечает на единственный вопрос: работает ли
контроль. Пропал heartbeat — плагин не работает. Это вопрос к процессу, а не к
конкретной команде, которую вы выполнили.

## 4. Установка

```bash
git clone <репозиторий плагина> ~/secure-dev
bash ~/secure-dev/deploy/install.sh
```

Затем в Claude Code:

```
/plugin marketplace add ~/secure-dev
/plugin install secure-dev@secure-dev-marketplace
```

Проверка:

```bash
secure-dev doctor
```

Установщик делает три вещи: ставит CLI в `~/.local/bin`, доливает
рекомендуемые правила в `~/.claude/settings.json` (с резервной копией) и
добавляет в `~/.bashrc` обёртку, которая проверяет незнакомый репозиторий до
запуска `claude`.

### Требования

- **WSL2/Ubuntu.** Запуск вне WSL плагин не блокирует, но предупреждает: разбор
  команд рассчитан на bash, и на другой платформе часть контролей не
  гарантирована.
- **python3 3.8+.** Внешних зависимостей нет и не будет.

## 5. Рекомендуемые настройки — что именно они запрещают

Файл `~/.claude/settings.json` работает независимо от плагина. В нём:

- запрет чтения `.env`, `~/.ssh`, `~/.aws`, `*.pem`, `.netrc`, `.pgpass`,
  учётных данных Claude Code;
- запрет правки `~/.bashrc`, `~/.zshrc`, `.envrc`, чужих хуков;
- запрет `sudo`, `doas`, `pkexec`;
- подтверждение для `git push`, `docker`, `WebFetch`;
- `enableAllProjectMcpServers: false` — MCP-серверы из репозитория не
  подключаются автоматически;
- отключение необязательной телеметрии.

Ваши собственные правила при установке не теряются: правила шаблона
доливаются к существующим.

## 6. Что делать, когда контроль мешает

Сначала — прочитать сообщение. В нём есть альтернатива, и в большинстве случаев
она короче обходного пути.

Если альтернатива не подходит:

1. Выполните операцию сами в отдельном терминале. Для `sudo` это единственный
   штатный путь: агенту root не выдаётся по политике.
2. Если операция нужна регулярно — заявка в `#secure-dev`, SLA один рабочий
   день. В заявке: id правила, команда, зачем она нужна, предлагаемый срок
   исключения.

Отсутствие быстрого канала эскалации — главная причина, по которой такие
контроли саботируются. Канал есть, пользуйтесь им.

Ужесточить контроль для себя можно всегда:

```json
{ "level": "strict" }
```

в `~/.claude/secure-dev.local.json`. Смягчить — нельзя: попытка игнорируется и
попадает в журнал.

## 7. Чего плагин не делает

- Не ищет уязвимости в вашем коде (SQLi, XSS, RCE). Для этого —
  `/security-review`, `anthropics/claude-code-security-review` в CI, semgrep.
- Не проверяет качество и дублирование кода.
- Не изолирует процесс: контейнеры, сетевой прокси и sandbox — слой ОС.
- Не заменяет secret scanning в CI. Gitleaks и trufflehog остаются; плагин
  закрывает окно между появлением секрета и коммитом.
- Не читает и не хранит ваш диалог с моделью.
