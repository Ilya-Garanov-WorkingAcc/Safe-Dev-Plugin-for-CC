# Постмортем: домашний каталог WSL стёрт агентом через `rsync --delete` (18.09.2026)

## Кратко

18 сентября 2026 в 14:14 МСК сессия Claude Code (режим `auto`, cwd `~/projects`,
проект `ttd-report`) при сквозной проверке деплоя выполнила `rsync --delete`,
у которого назначение разрешилось в домашний каталог. `/home/igaranov` был
вычищен за ~20 секунд: остались только два файла-источника (`index.html`,
`data.json`) и каталоги, которые процесс не смог удалить. Вместе с домом ушли
плагины, `.credentials.json`, история агентов и все проекты без git.

Восстановление: копия vhdx на 14:10 того же дня импортирована как
`Ubuntu-restored`; потеряны 4 минуты работы.

## Почему не сработал ни один контроль

1. `~/.claude/hooks/destructive-guard.sh` существовал, но **не был подключён**
   в `settings.json`. И не знал про `rsync`.
2. Установлен был `safe-development 1.0.3` (только редактор секретов).
   `secure-dev 2.0.x` с `command_guard` лежал в репозитории, не установленный.
3. В `secure-dev 2.0.x` **не было правил для `rsync`**: класс
   `command-destructive` знал `rm`, `dd`, `mkfs`, но не синхронизацию.
4. Гейты AGGG4ks (`agent-gates.js`, `pi-gates.ts`) — regex-денлист без `rsync`;
   в pi блокировка отключена владельцем.
5. Режим `auto` + `skipDangerousModePermissionPrompt` — человек не участвовал.
6. Бэкапов не было: ни cron, ни задач планировщика, ни экспортов дистрибутива.
7. Прикладная причина: тест деплоя гонялся на **реальных путях** (`$HOME`),
   а не в `mktemp -d`.

## Что изменено

**secure-dev 2.1.0** (эта версия):

- Правила по **назначению** синхронизации (`dest_root`, `dest_outside_cwd`,
  `dest_dynamic`, `dest_regex_any`): `rsync --delete*` /
  `--remove-source-files` в `~`, `/`, предок cwd, `localhost:` → CRITICAL deny;
  переменная/подстановка в назначении, удалённый хост, вне cwd → ask; внутри
  проекта → warn. Плюс `find -delete`, `shred`, `wsl --unregister`,
  `docker system prune --volumes`, `chown -R /`, `tar -x -C ~`, `cp -r … ~/`.
- **Прозрачность скриптов**: `bash x.sh`, `./x.sh`, `source x.sh` — файл
  читается и разбирается теми же правилами. Инцидентная команда была внутри
  скрипта, по командной строке её не видно.
- Парсер: `--del` → `--delete-during`, value-флаги rsync (`-e ssh`,
  `--exclude x`), поле `argv0_text` с путём как написано.
- Корпус: 22 обязательных deny, 17 ask, 11 разрешённых, 12 сценариев со
  скриптами.

**Вне плагина:**

- Ежедневный `tar.gz` дома и еженедельный `wsl --export` (задачи планировщика
  Windows `WSL-Backup`, `WSL-Export`), без `--delete`, с проверкой назначения.
- Все проекты без git — в приватные репозитории.
- Денлист AGGG4ks дополнен теми же паттернами, с node-тестом.

## Уроки

- **Назначение важнее команды.** `rsync` безобиден, пока справа не оказался
  дом. Правила должны смотреть на операнд-цель, иначе они либо молчат, либо
  блокируют бэкапы.
- **Скрипт — не граница проверки.** Агент, которому нельзя набрать команду,
  напишет её в файл и запустит файл. Хук обязан заглядывать внутрь.
- **Тесты деплоя — только в песочнице.** `mktemp -d`, `bwrap`, контейнер;
  никогда `$HOME` и никогда `localhost:` без явного пути.
- **Бэкап — не зеркало.** `rsync --delete` в каталог бэкапа повторяет ту же
  ошибку в другом месте; версионные архивы дешевле и безопаснее.
- **Guard, который не подключён, равен отсутствующему.** Проверять не «есть
  ли файл хука», а «есть ли запись в settings.json и срабатывает ли она».
